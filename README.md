# Логические и векторные часы в распределённой системе

## 1. Описание проекта

Проект выполнен на Python в соответствии с заданием «Логические и векторные часы». Он моделирует три процесса, которые выполняют внутренние события и обмениваются пятью сообщениями. Для каждого события фиксируются логическая метка Лэмпорта и векторные часы. После симуляции вычисляются причинно-следственные связи, статистика конкурентности, строится диаграмма пространства-времени и демонстрируется обнаружение конфликтующих обновлений в версионируемом key-value хранилище.

Реализация использует детерминированный сценарий, чтобы результаты запуска были воспроизводимыми и их можно было описать в отчёте. Для визуализации используется `matplotlib`, для автоматических проверок — `pytest`.

## 2. Реализованные требования

- `LamportClock`: хранение счётчика, `increment()` и `update(received_timestamp)` по формуле `max(local, received) + 1`.
- `VectorClock`: вектор длины N, увеличение компоненты процесса, покомпонентное объединение через максимум, создание копии.
- `happens_before(v1, v2)`: проверка строгого причинного предшествования.
- `compare_vectors(...)`: определение отношений `BEFORE`, `AFTER`, `EQUAL` и `CONCURRENT`.
- `Simulation` и `Process`: три процесса, внутренние события, отправка и получение сообщений; каждая запись содержит обе временные метки.
- Причинно-следственный анализ: список всех упорядоченных пар `E_i -> E_j`, где вектор первого события строго предшествует вектору второго.
- Статистика: число событий, число неупорядоченных пар, причинно-связанных и конкурентных пар.
- `VersionedKV`: операции `put()` и `get()`, хранение значения и вектора версии, обнаружение конкурентных обновлений.
- Стратегии разрешения конфликтов: LWW (последнее полученное обновление побеждает) и Merge (числа складываются, строки соединяются через `|`).
- Диаграмма времени с линиями процессов, точками событий, подписями, стрелками сообщений и отдельным цветом для событий, помеченных как конфликтные.
- Набор unit-тестов для часов, причинного порядка и хранилища.

## 6. Как устроены логические часы Лэмпорта

У каждого процесса есть целочисленный счётчик. При внутреннем событии и отправке сообщения он увеличивается на единицу. При получении сообщения локальное значение сравнивается с меткой отправителя, после чего устанавливается:

```python
clock = max(local_clock, received_timestamp) + 1
```

Часы Лэмпорта позволяют согласованно упорядочить причинно связанные события, но сами по себе не позволяют надёжно определить конкурентность: разные события могут иметь одинаковые или сравнимые скалярные метки без достаточной информации о причинности.

## 7. Как устроены векторные часы

В системе из трёх процессов каждый вектор имеет вид `[P1, P2, P3]`. Компонента `i` отражает известное процессу число событий процесса `Pi`.

- При локальном событии или отправке сообщения процесс увеличивает собственную компоненту.
- При получении сообщения процесс выполняет покомпонентный максимум локального и полученного векторов, а затем увеличивает собственную компоненту.
- В сообщение передаётся копия вектора, чтобы последующие изменения часов отправителя не изменили уже отправленную метку.

Для векторов одинаковой длины выполняется `v1 → v2`, если каждая компонента `v1` не больше соответствующей компоненты `v2` и хотя бы одна компонента строго меньше. Если ни один вектор не предшествует другому и векторы не равны, события конкурентны.

## 8. Конфликты в key-value хранилище

Сценарий начинается со значения `x = 0` и версии `[0, 0, 0]`. Два процесса читают исходное значение независимо:

1. P1 вычисляет `x = 0 + 1 = 1` и отправляет версию `[1, 0, 0]`.
2. P2 вычисляет `x = 0 * 2 = 0` и отправляет версию `[0, 1, 0]`.
3. Ни один из этих векторов не предшествует другому — версии конкурентны, поэтому хранилище фиксирует конфликт.

### LWW (Last Write Wins)

В данной учебной реализации победителем считается последнее **полученное хранилищем** обновление. Это детерминированная замена физическому времени. Если первым записать P1, а затем P2, итог будет `x = 0`, версия `[1, 1, 0]`. Преимущество — простота; недостаток — одно из изменений теряется.

### Merge

Для чисел применяется `a + b`, для строк — `a + "|" + b`. В приведённом примере хранилище объединяет конфликтующие значения `1` и `0`, результат — `x = 1`, версия `[1, 1, 0]`. Такой merge соответствует формулировке задания, но в реальной системе семантика объединения должна подходить предметной области: сложение двух абсолютных значений не всегда эквивалентно корректному объединению операций.

## 9. Вывод причинно-следственных связей и статистики

`causal_relations(events)` перебирает пары событий и возвращает пары идентификаторов `(id_1, id_2)`, для которых `happens_before(vector_1, vector_2)` истинно. Это именно направленные причинные связи. `event_statistics(events)` отдельно рассматривает каждую неупорядоченную пару и относит её к причинно связанным, если один вектор строго предшествует другому, иначе — к конкурентным.

Равные векторы не трактуются как строгое причинное предшествование. При корректной симуляции разных событий одного процесса собственная компонента увеличивается, поэтому их векторы различаются.

## 10. Тестирование

Запуск тестов:

```bash
python -m pytest -v
```

Тесты проверяют:
- увеличение часов Лэмпорта и обновление по `max + 1`;
- копирование и объединение векторных часов;
- причинное предшествование и конкурентность;
- обнаружение конфликта в хранилище;
- поведение LWW и Merge;
- замену устаревшей причинной версии;
- обработку некорректных входных данных.

## 11. Примечания и ограничения

1. Симуляция детерминирована, а не случайна: так проще проверять результаты и воспроизводить диаграмму.
2. Временная ось диаграммы использует Lamport timestamp как логическую координату, а не физическое время. Разные события могут иметь одинаковые метки.
3. Два независимых обновления `x` добавлены в начало сценария симуляции и помечены `conflict=True`, поэтому на диаграмме они выделяются красным цветом. Их результаты также проверяются отдельно в демонстрации хранилища.
4. Хранилище демонстрирует базовую обработку конкурентных версий, а не промышленный протокол репликации: здесь нет сети, долговременного хранения, повторной доставки и согласования нескольких реплик.
